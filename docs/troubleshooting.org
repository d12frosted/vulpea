#+TITLE: Troubleshooting Vulpea
#+AUTHOR: Boris Buliga

Solutions to common issues with Vulpea.

* Start Here: vulpea-doctor

Before digging into specific symptoms, run:

#+begin_example
M-x vulpea-doctor
#+end_example

It reports versions, configuration, database state, sync state, and external tool availability in one buffer, and flags common problems automatically: missing sync directories, an empty database, =fswatch= / =fd= not visible to Emacs (a frequent =PATH= issue on GUI Emacs and Doom), autosync disabled, external monitoring that is configured but not running, and watchers still running on a =vulpea-db-sync-directories= value that has since changed. It is read-only - nothing is created or modified.

The Database section also reports =cached files= (how many files the change-detection cache tracks) and =files without notes= (how many of those produced no note). A non-zero =files without notes= is normal for genuinely note-less files (READMEs, drafts), but if notes you expect are missing, a high count points at files stuck in the cache - run =C-u M-x vulpea-db-sync-full-scan= to re-extract them.

If the report shows no issues but the problem persists, continue with the sections below - and include the report when [[*Getting Help][asking for help]].

* Notes Not Appearing

** Symptom

=vulpea-find= shows nothing, or specific notes are missing from queries.

** Causes and Solutions

*** Notes lack ID properties

Vulpea only indexes entries with =ID= properties.

*Check:* Open a note and look for the property drawer:

#+begin_src org
:PROPERTIES:
:ID: some-uuid-here
:END:
#+end_src

*Fix:* Add ID with =M-x org-id-get-create=

*** Directory not configured

*Check:*

#+begin_src emacs-lisp
(message "%S" vulpea-db-sync-directories)
#+end_src

*Fix:* Add your notes directory:

#+begin_src emacs-lisp
(setq vulpea-db-sync-directories '("~/org/"))
#+end_src

If =vulpea-db-autosync-mode= was already on when you changed the variable, toggle it off and on: the watchers read the value when the mode starts, so a running watcher keeps the old directory list (see [[*Watcher started before a directory change][Watcher started before a directory change]]).

*** Database not synced

*Check:*

#+begin_src emacs-lisp
(vulpea-db-count-notes)  ; Should be > 0
#+end_src

*Fix:* Run initial sync:

#+begin_src emacs-lisp
(vulpea-db-sync-full-scan)
#+end_src

*** Note is ignored

Notes whose exclusion property is set to a non-nil value are excluded.
By default that property is =VULPEA_IGNORE= (configurable through
=vulpea-db-exclude-property=).

*Check:* Look for the property:

#+begin_src org
:PROPERTIES:
:VULPEA_IGNORE: t
:END:
#+end_src

*Fix:* Remove the property, or set it to =nil=, if you want the note
indexed.

*** Note is ignored because of an ancestor

A note can also be excluded without carrying any property itself, when
something above it excludes its descendants. This is the case where the
marker is not on the note you are looking at, so it is easy to miss.

*Check:* Look for =VULPEA_IGNORE_CHILDREN= (configurable through
=vulpea-db-exclude-children-property=) on any ancestor heading of the
missing note, and in the file-level property drawer, which applies to
every heading in the file:

#+begin_src org
,* Meetings
:PROPERTIES:
:VULPEA_IGNORE_CHILDREN: t
:END:

,** This heading is not indexed, however deep it sits
#+end_src

Note that the ancestor carrying it does not have to be a note itself: a
heading with no =ID= still excludes everything below it.

*Fix:* Remove the property, or set it to =nil=. If you want the
container excluded but its children indexed, use =VULPEA_IGNORE= on the
container instead: that is the other property.

*** Note not found by alias

By default, vulpea uses the property =ALIASES=. When migrating from org-roam, you
might have them in =ROAM_ALIASES=. You can fix it by either:

*Fix A:* Override default
#+begin_src emacs-lisp
(setq vulpea-buffer-alias-property "ROAM_ALIASES")
#+end_src

or

*Fix B:* rename =ROAM_ALIASES= in all files to =ALIASES= if you don't need backwards compatibilty any more.

* Slow Performance

** Slow Startup

*** Symptom

Emacs hangs when enabling =vulpea-db-autosync-mode=.

*** Cause

=vulpea-db-sync-scan-on-enable= is set to ='blocking=, so the initial
scan processes every file before the mode returns.

*** Solutions

1. *Use the async scan* (the default):

   #+begin_src emacs-lisp
   (setq vulpea-db-sync-scan-on-enable 'async)
   #+end_src

   Enabling the mode then returns in a few milliseconds (10ms
   for 14k notes, see =bench/README.md=). File listing runs as a
   subprocess (=fd= or =find=), and changed files are processed in
   batches from an idle timer.

2. *Skip startup scan entirely:*

   #+begin_src emacs-lisp
   (setq vulpea-db-sync-scan-on-enable nil)
   #+end_src

3. *Run sync manually* when convenient:

   #+begin_src emacs-lisp
   (vulpea-db-sync-full-scan)
   #+end_src

** Slow Sync Operations

*** Symptom

Full scans take a long time, even on subsequent runs.

*** Solutions

1. *Install =fd=* for faster file discovery:

   #+begin_src bash
   brew install fd        # macOS
   apt install fd-find    # Debian/Ubuntu
   pacman -S fd           # Arch
   #+end_src

2. *Use faster parse method:*

   #+begin_src emacs-lisp
   (setq vulpea-db-parse-method 'single-temp-buffer)
   #+end_src

3. *Disable heading indexing* if you only use file-level notes:

   #+begin_src emacs-lisp
   (setq vulpea-db-index-heading-level nil)
   #+end_src

** A Long Scan Slows Down as It Goes

*** Symptom

A full scan starts at hundreds of files per second and ends at a
crawl.

*** Cause

With stock org-mode a full scan holds its rate: on the bench harness
the default =temp-buffer= method takes about 20s for every 10k files,
from the first 10k to the last of 100k (see =bench/README.md=). So a
scan that slows down points at something that runs for every file and
gets slower the more files it has seen, usually a function on
=org-mode-hook=: =temp-buffer= re-runs =org-mode= for every file, and
the hook with it.

Vulpea versions up to 2.7 had such a slowdown of their own: org
registered every parsed file with its persistent element cache
(=org-persist=), and each file took longer than the one before (100k
files took 18 minutes instead of 3.3). On those versions, =(setq
org-element-cache-persistent nil)= avoids it.

*** Solution

Either switch to =single-temp-buffer=, which never re-runs the hooks
(see [[file:configuration.org::*Parse Method][Parse Method]] for what you give up), or keep the method and guard
the heavy hooks so they skip Vulpea's parse buffers:

#+begin_src emacs-lisp
(add-hook 'org-mode-hook
          (lambda ()
            (unless (bound-and-true-p vulpea-db--active-parse-method)
              ;; Your heavy code here
              )))
#+end_src

* External Changes Not Detected

** Symptom

Files modified by git, Dropbox, or other tools don't update in the database.

** Solutions

*** Install fswatch

The most reliable solution:

#+begin_src bash
brew install fswatch      # macOS
apt install fswatch       # Debian/Ubuntu
pacman -S fswatch         # Arch
#+end_src

*** Make sure Emacs can find fswatch

Vulpea locates =fswatch= (and =fd=) via =executable-find=, which uses Emacs's own =PATH= - not your shell's. GUI Emacs often starts with a minimal =PATH=, so the tools may be installed yet invisible. Check:

#+begin_src emacs-lisp
(executable-find "fswatch") ; should return a path, not nil
(executable-find "fd")
#+end_src

If either returns =nil=:

- *Doom Emacs:* Doom snapshots your environment into an env file. Re-run =doom env= after installing the tools, then restart Emacs.
- *Other setups:* use [[https://github.com/purcell/exec-path-from-shell][exec-path-from-shell]] or add the install location to =exec-path= manually.

With =vulpea-db-sync-external-method= set to ='auto= (the default), a missing =fswatch= causes a /silent/ fallback to polling - the only trace is a one-line message in =*Messages*= at startup.

*** Configure external detection

#+begin_src emacs-lisp
;; Auto-detect best method (recommended)
(setq vulpea-db-sync-external-method 'auto)
#+end_src

*** Verify fswatch is running

The "external monitoring" line of =M-x vulpea-doctor= shows whether
fswatch is running. With =vulpea-db-sync-verbose= on (the default),
=*Messages*= also shows:

#+begin_example
Vulpea: Started fswatch monitoring
#+end_example

*** Fallback to polling

If fswatch isn't available:

#+begin_src emacs-lisp
(setq vulpea-db-sync-external-method 'poll)
(setq vulpea-db-sync-poll-interval 2)  ; seconds
#+end_src

*** Watcher started before a directory change

If you changed =vulpea-db-sync-directories= while =vulpea-db-autosync-mode= was on, the running watcher does not know about it: the variable is read when the mode starts (=fswatch= receives the directories as command-line arguments; the same applies to the built-in filenotify watchers). Files under a newly added directory are then never synced on save, while manual commands like =M-x vulpea-db-sync-full-scan= read the current value and work - which makes the problem look like anything but configuration.

*Check:* =M-x vulpea-doctor= compares what the watcher was started with against the current value and reports a mismatch.

*Fix:* Toggle the mode:

#+begin_src emacs-lisp
(vulpea-db-autosync-mode -1)
(vulpea-db-autosync-mode +1)
#+end_src

*Prevention:* Change the list with =M-x vulpea-db-sync-add-directory=
and =M-x vulpea-db-sync-remove-directory= instead of =setq= - they
update the running watcher directly and scope the work to the
affected directory, so no toggle and no full rescan.

*** Windows: fswatch path styles

Vulpea passes =fswatch= the note directories as =expand-file-name=
produces them (e.g. =c:/Users/you/notes=).  Two =fswatch= builds are
common on Windows and they take different directory arguments:

- *MSYS2/mingw* (=c:/msys64/mingw64/bin/fswatch.exe=) watches native
  =c:/...= paths directly.
- *Cygwin* (e.g. from winget) only watches =/cygdrive/c/...= paths and
  errors out on native ones.

Both work out of the box.  =vulpea-db-sync-fswatch-path-style= defaults
to =auto=: vulpea starts with native paths and, if it sees the Cygwin
build's path errors, automatically restarts the watcher with translated
=/cygdrive/= directories.  If you'd rather skip the probe, set it
explicitly:

#+begin_src emacs-lisp
;; Force a specific build's path style
(setq vulpea-db-sync-fswatch-path-style 'cygwin) ; or 'native
#+end_src

If external changes still are not detected on Windows, check which
=fswatch= =M-x vulpea-doctor= reports under External Tools.  See
[[https://github.com/d12frosted/vulpea/issues/344][vulpea#344]].

*** Symlinked note directories

A =vulpea-db-sync-directories= entry that is itself a symlink (a
Termux storage link, an iCloud or Dropbox path) is supported: the
file watcher lands on the link's target and events are matched back
to the configured path.  Symlinked directories /inside/ a note
directory are a different story - they are deliberately not followed
(a link pointing back at an ancestor would loop the watcher), so
notes behind them are invisible to sync.  List the real location (or
the link itself) as its own entry in =vulpea-db-sync-directories=
instead.

* Links Cannot Be Followed

** Symptom

=vulpea-find= finds a note, but following an =id:= link to it fails with "Cannot find entry with ID". Opening the note by hand and re-saving it makes the link work.

** Cause

Vulpea finds notes through its own database. Org follows =id:= links through =org-id-locations=, a separate index that vulpea fills as it indexes files, and that org saves only when Emacs exits. A session that was killed, two Emacs sessions on one vault (each saves its own copy at exit, the last one wins), or a moved or missing =org-id-locations-file= leaves org's index behind. Nothing in normal operation repairs it, because files that did not change are never indexed, and so never registered, again.

** Solution

Scans repair this on their own: every batch registers what org's index is missing for the files it skipped as unchanged, without reading them, so the initial scan of =vulpea-db-autosync-mode= and a smart =vulpea-db-sync-full-scan= both leave the index complete. If you scan nothing on enable (=vulpea-db-sync-scan-on-enable= set to nil), or want to repair the whole database at once, run:

#+begin_src emacs-lisp
M-x vulpea-db-register-org-ids
#+end_src

It reports how many ids it had to register. A forced =vulpea-db-sync-full-scan= repairs the index too, by re-reading every file, which on a large collection takes much longer.

* Database Issues

** Stale or Incorrect Data

*** Symptom

Queries return outdated information or wrong results.

*** Solution

Rebuild the database:

#+begin_src emacs-lisp
;; Force complete re-index
(vulpea-db-sync-full-scan 'force)
#+end_src

Or with =C-u= prefix: =C-u M-x vulpea-db-sync-full-scan=

** Notes Missing After an Upgrade or External Sync

*** Symptom

Some notes never show up in =vulpea-find=, even after a normal sync.
Editing and re-saving an affected file (or running a force scan)
makes it appear.

*** Cause

Vulpea keeps a per-file change-detection cache (mtime/size/hash) and
skips files that have not changed since they were last seen.  If a
file was once indexed while it produced no note - for example a
partially-synced cloud file, or an older Vulpea version that failed to
extract its =ID= - that "no note" result was cached.  A normal scan
then keeps skipping the file (its content has not changed), so it
stays invisible until the file is edited.

*** Solution

Vulpea now invalidates this cache automatically when its extraction
logic changes (the parser epoch), so upgrading re-extracts every file
once and heals such notes.  To fix it immediately without waiting:

#+begin_src emacs-lisp
;; Force complete re-index, ignoring the change-detection cache
(vulpea-db-sync-full-scan 'force)
#+end_src

Or with =C-u= prefix: =C-u M-x vulpea-db-sync-full-scan=

** Stale Data After Editing .dir-locals.el

*** Symptom

You use a parse method that applies dir-locals (=find-file= or
=temp-buffer=; only =single-temp-buffer= skips them) or an extractor
that reads dir-locals, and edited a =.dir-locals.el=, but queries
still return values computed from the old settings.

*** Cause

Note files themselves did not change, so change detection skips them.
Autosync re-indexes the affected subtree automatically when it sees a
dir-locals change (see =vulpea-db-sync-reindex-on-dir-locals-change=,
default =auto=) - if you see stale data anyway, either the reaction
is disabled, autosync was off while the file changed and no scan ran
since, or the variables come from a directory class defined in elisp
(=dir-locals-set-class-variables=), which has no file to watch.

*** Solution

Re-index the affected directory manually:

#+begin_src emacs-lisp
(vulpea-db-sync-update-directory "~/notes/project" 'force)
#+end_src

Or force a full scan: =C-u M-x vulpea-db-sync-full-scan=

** Database Corruption

*** Symptom

SQLite errors (=database disk image is malformed= and the like) on
every query, and a forced scan does not clear them.

*** Solution

Delete and rebuild:

#+begin_src emacs-lisp
;; Close database
(vulpea-db-close)

;; Delete file
(delete-file vulpea-db-location)

;; Rebuild
(vulpea-db-sync-full-scan)
#+end_src

* Template Issues

** Template Expansion Not Working

*** Symptom

Placeholders like =${title}= appear literally in created notes.

*** Causes

1. *Unknown placeholder:* only =${title}=, =${slug}=, =${timestamp}= and =${id}= are built in. Any other =${key}= is replaced only when the =:context= plist passed to =vulpea-create= has a matching =:key=; otherwise it is left as is.

2. *Directive inside a value:* =%(...)= and =%<...>= are expanded in the template itself, before values are substituted, so the same text inside a title or a =:context= value stays literal. This is deliberate: a note title is data and never runs as code.

A =%(...)= expression that signals an error expands to =ERROR: ...= rather than staying literal. See [[file:configuration.org::*Template Expansion Syntax][Template Expansion Syntax]].

* Compatibility Issues

** With org-roam

Vulpea v2 is independent from org-roam. Both can coexist:

- They maintain separate databases
- No configuration overlap
- Use either or both for queries

** With Doom Emacs

See the [[file:getting-started.org][Getting Started guide]] for the recommended =packages.el= / =config.el= setup. Common Doom-specific pitfalls:

1. *=fswatch= / =fd= not detected:* Doom snapshots your shell environment into an env file, so tools installed afterwards are invisible to GUI Emacs. Re-run =doom env= and restart. See [[*Make sure Emacs can find fswatch][Make sure Emacs can find fswatch]].

2. *Running an old version:* =package!= installs a MELPA snapshot that is only updated when you run =doom sync -u= - just restarting Emacs does not update packages. Check what you are actually running with =M-x vulpea-version= before reporting bugs.

3. *=org-directory= mismatch:* Doom's =:lang org= module sets =org-directory= (default =~/org/=), and Vulpea derives its defaults from it at load time. If your notes live elsewhere, set =org-directory= (or =vulpea-db-sync-directories=) in =config.el= /before/ Vulpea loads.

** With Other Packages

With the default =temp-buffer= method, Vulpea loads each note into a
reused buffer and re-runs =org-mode= there. =buffer-file-name= is set,
but it is not a real visit: =find-file-hook= does not run.
(Dir-locals and file-local variables do apply, since the =org-mode=
rerun hacks them.) A package whose =org-mode-hook= function depends on
a real visit can misbehave in that buffer. Two ways
out: guard that function with =vulpea-db--active-parse-method= (see
[[*A Long Scan Slows Down as It Goes][above]]), or parse with real file visits:

#+begin_src emacs-lisp
(setq vulpea-db-parse-method 'find-file)  ; slowest, runs every hook as usual
#+end_src

* Async Extraction Issues

First stop: =M-x vulpea-db-worker-diagnose=. It runs an end-to-end
health check and tells you whether your files actually use the
worker, why not if they don't, the database journal mode, round-trip
timing, and the worker's stderr.

** Async is enabled but saves still block

Almost always: a registered extractor plugin declaring
=:requires-ast t=. The AST cannot cross the process boundary, so an
AST-reading extractor routes *every* file to the synchronous path.
Both =vulpea-doctor= and =vulpea-db-worker-diagnose= report this.
Extractors without that declaration are harmless here - they run
against a nil-AST context in the main process (see the plugin
guide).

The related trap points the other way: an extractor that reads the
AST but /forgot/ to declare =:requires-ast t= extracts nothing,
because undeclared extractors always receive a nil AST. If a plugin's
table stays empty, check its declaration first.

** Full mode configured, but writes happen on the main thread

='full= degrades to =t= when:

- WAL journaling failed (network/FUSE filesystems);
- note index filters are active (schema validation with a non-silent
  action, or a custom filter);
- a registered extractor is not declared =:worker-safe=, or the worker
  cannot load one that is;
- the worker's vulpea differs from the session's (a stale load path or
  byte-code; restart after upgrading).

=M-x vulpea-doctor= reports the first two. =M-x
vulpea-db-worker-diagnose= shows whether full-write is in effect, and
its worker stderr tail names a version mismatch.

** Worker marked broken

When the worker cannot start, crash-loops, or hangs repeatedly,
vulpea stops respawning it and falls back to synchronous indexing.
The warning says why (for a crash loop, with the worker's stderr
tail). Investigate with
=M-x vulpea-db-worker-diagnose=, then =M-x vulpea-db-worker-reset=
to re-arm. For a full protocol trace, =(setq vulpea-db-worker-debug
t)= and read =*vulpea-worker-log*=.

** Data seems stale right after saving

Worker-extracted files become queryable when the background sync
completes (watch for the "background sync complete" message), a
moment after the save. Programmatic APIs (=vulpea-create=,
=vulpea-meta-set=) are unaffected - they are synchronous and
read-your-writes. If code queries small files right after saving
them, set =vulpea-db-async-extraction-threshold= to keep small files
synchronous.

** WAL sidecar files appeared next to my database

Expected in ='full= mode: SQLite's write-ahead log creates =-wal=
and =-shm= files. They are part of the database - include them in
backups, and do not delete them while Emacs runs.

* Getting Help

If none of these solutions work:

1. *Check existing issues:* [[https://github.com/d12frosted/vulpea/issues][GitHub Issues]]

2. *Open new issue* with:
   - The full report from =M-x vulpea-doctor= (covers versions, configuration, database and sync state in one paste)
   - Steps to reproduce
   - Error messages (from =*Messages*= buffer)

   On older versions without =vulpea-doctor=, collect the equivalent manually:

   #+begin_src emacs-lisp
   (message "Vulpea version: %s" (vulpea-version))
   (message "Vulpea dirs: %S" vulpea-db-sync-directories)
   (message "DB location: %s" vulpea-db-location)
   (message "Note count: %d" (vulpea-db-count-notes))
   (message "Autosync: %s" vulpea-db-autosync-mode)
   #+end_src
