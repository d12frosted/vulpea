#+title: Comparison with Other Libraries
#+author: Boris Buliga

This document compares Vulpea with other Org-mode note management libraries: [[https://github.com/org-roam/org-roam][org-roam]], [[https://github.com/meedstrom/org-node][org-node]] and [[https://github.com/yibie/supertag][Supertag]].

* Disclaimer

I have not used org-node or Supertag myself; what I say about them comes from their READMEs, documentation and source code. If you notice any inaccuracies, please open an issue or pull request.

Last updated: 2026-09-24, against org-roam 2.3.1, org-node 3.18 with org-mem 0.34, and Supertag V2 (package version 6.0.0).

* Overview

All four index Org files and use =org-id= to identify notes: a file or a heading with an =ID= property is something you can find, link to and see backlinks for. They differ in what they optimize for and in how they keep their index in step with your files.

| Aspect      | org-roam               | org-node                         | Supertag                            | vulpea                                 |
|-------------+------------------------+----------------------------------+-------------------------------------+----------------------------------------|
| Built for   | Roam Research in Emacs | Fast org-id notes, org-roam data | Write first, organize later         | Notes as queryable data, with an API   |
| Storage     | SQLite                 | In-memory, rebuilt each session  | In-memory, saved to one Elisp file  | SQLite                                 |
| Parser      | org-element            | Custom regexp parser (org-mem)   | org-element                         | org-element                            |
| Updates on  | Save hook              | Save hook, periodic full reset   | Save queue, periodic scan (15 min)  | File watchers, optional worker process |
| Other Emacs | Shared DB              | Each session builds its own      | Reloads a newer DB file when idle   | Shared DB, each session watches files  |

* Design Philosophy

** org-roam

Org-roam replicates [[https://roamresearch.com/][Roam Research]] in Emacs. It comes as a complete note-taking system: its own capture templates (=org-roam-capture-templates=), a =roam:= link type, a backlinks buffer, daily notes, graph export and a protocol handler for the browser (=org-roam-protocol=). You adopt its workflow.

Its biggest strength is its community: the largest ecosystem of third-party packages (org-roam-ui, org-roam-bibtex, consult-org-roam and more), forums, and documentation. If you need help, you'll find it.

** org-node

Org-node started as "org-roam but faster" and grew into its own package on top of [[https://github.com/meedstrom/org-mem][org-mem]]. Org-mem reads all your Org files with a small custom parser in parallel subprocesses, keeps the result in memory, and rebuilds it from scratch fast enough that nothing needs to be persisted; its author reports 2418 files in 1.95s. It can also mirror the data into an org-roam-compatible SQLite database.

Org-node uses the same on-disk format as org-roam, so there is nothing to migrate, and it adds utilities org-roam lacks: renaming files when a title changes, fixing stale link descriptions, listing dead links, warning about duplicate titles, node sequences (for dailies and other series), and backlinks written into the files themselves.

** Supertag

Supertag (formerly org-supertag) released V2 in September 2026 with a narrower goal: make writing notes feel effortless, and move every organizing decision to later. V2 dropped typed fields and its own capture flow. You write with plain =org-capture=; a heading becomes a note once it has an =ID=.

Organizing then happens in the text and in views built on Supertag's index:

- inline =#tags= with completion, including nested tags (=#emacs/package/elpa= records the hierarchy)
- =supertag-promote= turns a selection or heading into a note from a template, leaving a link behind
- a node view with unlinked mentions and, optionally, semantically similar notes from a local embedding service
- stream and discovery views for rereading notes by tag or at random
- an S-expression query language for Babel and dynamic blocks
- automation rules that write back to the Org file
- Git-based sync of the Org text between machines

It's an application with a clear opinion about how to work.

** vulpea

Vulpea is a tool and a library at once. The commands (finding and linking notes, backlinks and unlinked mentions, renaming, moving, splitting and merging notes, schemas for structured notes) are built on the same public API you get: the =vulpea-note= struct and query functions. The database schema stays internal, so it can change without breaking code built on it.

With [[https://github.com/d12frosted/vulpea-ui][vulpea-ui]] and [[https://github.com/d12frosted/vulpea-journal][vulpea-journal]] it covers what org-roam does for everyday note-taking. Applications like [[https://github.com/d12frosted/vino][vino]] (wine cellar management) use it as a data layer.

* Architecture Deep Dive

** Parsing

*** org-roam, Supertag and vulpea: org-element

All three use Org's own parser, so they see a file the way Org does, at the cost of a slower parse. Vulpea softens that cost in two ways: by default it parses at =element= granularity, skipping inline objects that extraction never reads (the parse itself runs about 2.6x faster than a full one, with links located by org's own link parser so link semantics are unchanged), and it can run the whole parse in a background Emacs process (see Sync below).

*** org-node: org-mem's custom parser

Org-mem deliberately avoids Org's code. Its README gives three reasons: Emacs init should not have to load Org before notes can be searched, browsing should keep working when a customized Org setup breaks, and a full rebuild should be fast enough to replace cache invalidation. The parser is regexp-based and runs in parallel subprocesses. It reads headings, IDs, tags, properties, links and timestamps; it does not see everything Org does.

** Data Storage

*** org-roam: SQLite

Persisted to disk, and queried with SQL. The schema is effectively the API, with no stability guarantee from upstream. Several Emacs sessions writing the same database can hit "attempt to write a readonly database" errors.

*** org-node: in-memory, optional SQLite

Hash tables rebuilt in every session, fast lookups by ID. Full rebuild is fast: [[https://github.com/meedstrom/org-node#benchmarks-on-my-machine][org-node's README]] measures 2 seconds for its author's 3000 nodes. =org-mem-roamy-db-mode= also writes an org-roam-compatible SQLite database, which can even back org-roam's own queries; that database has the same multi-session caveat as org-roam's.

*** Supertag: in-memory, saved as Elisp

The index lives in hash tables and is saved as one serialized Elisp file (=supertag-db.el=), with daily backups. Some things exist only in that file and not in your Org text, such as automation rules. Another Emacs session that saves a newer revision is picked up when the local copy has no unsaved changes; across machines, Supertag recommends syncing the Org text with Git and letting each machine rebuild its own index.

*** vulpea: SQLite behind an API

Persisted to disk. The schema is an implementation detail; the public API is the =vulpea-note= struct and query functions. Several Emacs sessions share one database and each one's watchers index the changes it sees. Plugins can add their own tables (see [[file:plugin-guide.org][Plugin Guide]]).

** Directory Configuration

*** org-roam

=org-roam-directory= names a single directory tree; files outside it are ignored.

*** org-node

No dedicated directory. Org-mem indexes the files in =org-id-locations= (and =org-mem-watch-dirs= if set), so any file with an ID anywhere can hold nodes.

*** Supertag

=supertag-sync-directories=, set before loading the package. File-level IDs can come from org-roam's convention or Denote's (=supertag-file-id-source=).

*** vulpea

=vulpea-db-sync-directories= (defaults to =org-directory=), any number of directories.

** Sync

*** org-roam

Updates the database from =after-save-hook=. Saves of large files wait for the update, and changes made outside Emacs (git, Syncthing, Dropbox) are not seen until the file is saved in Emacs again or the database is rebuilt.

*** org-node

Updates the in-memory tables on save, and an idle timer triggers a full reset every now and then. Changes made outside Emacs show up after the next reset.

*** Supertag

Saving a file queues it, a periodic scan (every 15 minutes by default) queues files changed since the last sync, and the queue is processed while Emacs is idle. Unchanged files are skipped by content hash. After changing directories or moving machines, a full rescan rebuilds the index.

*** vulpea

File watchers queue every change, including ones made outside Emacs: fswatch reports them as they happen, and without it vulpea polls every few seconds. By default the queued files are parsed on the main thread, so a large file still freezes Emacs while it is indexed. With =vulpea-db-async-extraction= the parsing moves to a background =emacs --batch= worker, and in =full= mode the database write moves there too; see [[file:sync-architecture.org][Sync Architecture]].

* Feature Comparison

** Basic Note Taking

All four support:

- Finding notes by title (=org-roam-node-find=, =org-node-find=, =supertag-find-node=, =vulpea-find=)
- Inserting links (=org-roam-node-insert=, =org-node-insert-link=, =supertag-add-link=, =vulpea-insert=)
- Backlinks
- Tags

Aliases work in org-roam and org-node through =ROAM_ALIASES=; vulpea reads =ALIASES= by default (configurable via =vulpea-buffer-alias-property=).

Org-roam, Supertag and vulpea also show *unlinked mentions*: notes that name the current one in plain text without an =id:= link. In org-roam it is an opt-in =org-roam-mode= section (needs ripgrep); in Supertag it is part of the node view for concept notes (headings in its templates' target files); in vulpea it is =vulpea-note-unlinked-mentions-async=, shown as a vulpea-ui widget.

** Structured Data

*** org-roam

The =org-roam-node= struct has accessors for properties, tags, aliases, refs and more. Filling one in is expensive: =org-roam-populate= runs five queries per node (nodes, files, tags, aliases, refs). =org-roam-node-list= fetches all nodes with one larger query, but custom queries usually mean writing SQL.

*** org-node

Org-mem's entries carry properties, tags, links and timestamps, read through functions like =org-mem-entry-tags= and =org-mem-entry-property=. There is no separate metadata layer.

*** Supertag

V1 had typed fields attached to tags. V2 retired them; structured data now lives in ordinary Org properties, which the query language can match on (=(property "KEY" "value")=). Values from V1 fields can be written back to properties during migration.

*** vulpea

The =vulpea-note= struct is a complete note: id, title, tags, aliases, links, properties, metadata and more, read from a single row, so fetching many notes stays cheap.

On top of properties, vulpea has a *metadata system* built on Org description lists:

#+begin_src org
- rating :: 95
- producer :: [[id:xxx][Château Margaux]]
- date :: [2024-01-15]
#+end_src

The reason is links: Org does not treat links inside property drawers as links, so you can't point from a property to another note. Metadata can hold links, several values per key, and typed values (=vulpea-note-meta-get= parses numbers, dates, links and more on read), and it is queryable. Schemas declare which fields a kind of note should have and validate them.

** Querying

*** org-roam

SQL through =org-roam-db-query=, which means knowing the schema:

#+begin_src emacs-lisp
(org-roam-db-query
 [:select [title] :from nodes :where (= todo "TODO")])
#+end_src

*** org-node

Plain Lisp over org-mem's collections:

#+begin_src emacs-lisp
(seq-filter
 (lambda (entry)
   (member "project" (org-mem-entry-tags entry)))
 (org-mem-all-id-nodes))
#+end_src

*** Supertag

Its own S-expression query language, usable from Babel and dynamic blocks:

#+begin_src org
,#+BEGIN_SRC supertag-query-block :results raw
(and (tag "task") (todo "TODO"))
,#+END_SRC
#+end_src

*** vulpea

Query functions over the database, or any predicate over notes:

#+begin_src emacs-lisp
;; By tags
(vulpea-db-query-by-tags-every '("wine" "tasted"))

;; By links
(vulpea-db-query-by-links-some (list producer-id) "id")

;; Any predicate, here on metadata
(vulpea-db-query
 (lambda (note)
   (>= (or (vulpea-note-meta-get note "rating" 'number) 0)
       90)))
#+end_src

** Building on Top

*** org-roam

Many packages do (org-roam-ui and the rest), usually by querying its tables directly, which ties them to the schema.

*** org-node

Org-mem is meant to be used by other code: its entries and functions are a public, documented surface, and it is available on GNU ELPA independently of org-node.

*** Supertag

Its extension surface is the query language and automation rules (triggers, conditions and actions, created from templates).

*** vulpea

The API is the product, and it has kept code built on it working through a full backend rewrite. Accessors and query functions are ordinary functions, so the byte compiler flags typos and wrong arity that raw SQL only reveals at runtime. Packages built on it include [[https://github.com/d12frosted/vulpea-ui][vulpea-ui]], [[https://github.com/d12frosted/vulpea-journal][vulpea-journal]], [[https://github.com/d12frosted/vulpea-para][vulpea-para]] and third-party ones like [[https://github.com/fabcontigiani/consult-vulpea][consult-vulpea]] and [[https://github.com/fabcontigiani/embark-vulpea][embark-vulpea]]; note selection reports a =vulpea-note= completion category, so marginalia and embark work with it directly. The README's Ecosystem section has the full list.

* When to Choose What

** Choose org-roam if:

- You want the Roam Research experience in Emacs, including =roam:= links
- You want the largest community and third-party ecosystem
- Its speed is fine for your collection

** Choose org-node if:

- You use org-roam and find it too slow; the data stays compatible
- You want to stay close to vanilla Org (=org-capture=, =org-id=) with no directory setup
- You want its maintenance utilities (renaming files, fixing link descriptions, finding dead links)

** Choose Supertag if:

- You want to write first and organize later, with inline tags, promotion into notes and review views
- You want rule-based automation over your notes
- You want optional semantic "similar notes" from a local model

** Choose vulpea if:

- You want notes as structured, queryable data (metadata, schemas, properties)
- You want to build workflows or applications on a stable API
- You change files outside Emacs or run several Emacs sessions on one collection
- You have large files or a large collection and want indexing off the UI thread
- You want an org-roam replacement (with vulpea-ui and vulpea-journal), or to run alongside org-roam while you decide

* Coexistence

All four keep their own index and read the same kind of files, so they can index one collection side by side: org-node and org-roam even share the on-disk format, Supertag can take file-level IDs from org-roam's or Denote's convention, and vulpea keeps its database separate from all of them. That makes evaluating one or migrating gradually easy.

* Performance Notes

I have not benchmarked org-roam, org-node or Supertag myself, so the numbers here are vulpea's own, from [[file:../bench/README.md][bench/README.md]]; org-node's figures above are from its README.

A full sync of 100k generated notes takes 2.0 minutes with =single-temp-buffer= parsing and 3.3 with the default =temp-buffer=, at a steady rate from the first file to the last. With autosync on, it runs in the background.

The freeze you actually feel is the save of a large file:

| Save-path freeze  | sync path | worker (=t=) | worker (=full=) |
|-------------------+-----------+--------------+-----------------|
| 1MB file          | 252ms     | 43ms         | 12ms            |
| 10MB file         | 2.28s     | 0.45s        | 1.1ms           |

In =full= mode the worker writes the database itself, so the freeze stays flat (1.3ms at 100MB); the 1MB figures are mostly the first request of a session spawning the worker.

* Summary

| Library  | Best described as                                |
|----------+--------------------------------------------------|
| org-roam | Roam Research for Emacs                          |
| org-node | org-roam's data model, fast and close to Org     |
| Supertag | Write first, organize later                      |
| vulpea   | Notes as queryable data, with an API to build on |

For plain note-taking, any of them will do. If you want to build on top of your notes, that is what vulpea's API is for.

* Notes

** Encrypted files

org-roam indexes =.gpg= and =.age= files; org-node/org-mem support whole-file =.gpg=/=.age= with extra config (org-crypt-encrypted entry bodies stay opaque to the parser). vulpea supports them opt-in: set =vulpea-db-extra-extensions= to e.g. =(".org.age" ".org.gpg")= and install the matching decryption package (=age.el=, or the built-in =epa-file=); those files are parsed via the slower =find-file= method so the hooks can decrypt them (and always on the synchronous path - the background extraction worker does not decrypt). I haven't checked Supertag's support.

The caveat is the same everywhere: the extracted metadata (titles, tags, links) is stored in an *unencrypted* index. If a file's contents are secret, its title and tags usually are too, so indexing them partially defeats the purpose. That is a trade-off to weigh, not a blocker; in vulpea, change detection runs on the raw (still-encrypted) bytes.
