#+TITLE: Vulpea User Guide
#+AUTHOR: Boris Buliga

This guide covers daily usage of Vulpea - finding notes, creating links, and working with metadata.

* Finding Notes

** vulpea-find

The primary way to navigate your notes:

#+begin_example
M-x vulpea-find
#+end_example

This opens a completion interface showing all your notes. Type to filter, then select a note to open it.

Features:
- Searches titles and aliases
- Shows tags in the completion display
- Resolves a fully typed id to the existing note (see [[*Selecting by Id][Selecting by Id]])
- Creates a new note if you enter a title that doesn't exist

** Selecting by Id

Titles are not the only interactive handle: every note's id is part of
its completion candidate too, so you can type or paste an id to reach
the note. Type it in =vulpea-find= and it visits the note; do the same
in =vulpea-insert= and it links the note. This is most useful when ids
are structured and meaningful while titles are incidental or absent -
say contact cards with ids like =person:lectia= (see [[*Untitled Micro-Notes][Untitled Micro-Notes]]):

#+begin_example
M-x vulpea-find RET person:lectia RET
#+end_example

The id is carried invisibly: it is in the candidate string so
completion can match it, but hidden so it never clutters the list -
the same idea as tags and aliases being matchable. Typing an id
narrows the list to that note as you go, and you then select the note
like any other candidate. How much you must type depends on your
=completion-styles=, the same as for tags and aliases: interior styles
like =substring=, =flex= or =orderless= match an id anywhere in the
candidate, a strict prefix style only from the start. Set
=vulpea-select-match-ids= to nil to drop ids from matching.

For =vulpea-insert= the link description follows the usual rule: the
region text when a region is active, otherwise
=vulpea-insert-default-description-fn= (the note title by default).
The =id:= target is always kept behind a description, so the raw id is
never shown. When the note is untitled its title is the file base
name, which may be noise - point the function at the id (a good
description when ids are structured like =person:lectia=) or at a
combination of both:

#+begin_src emacs-lisp
;; use the id
(setq vulpea-insert-default-description-fn #'vulpea-note-id)

;; title and id together
(setq vulpea-insert-default-description-fn
      (lambda (note)
        (format "%s (%s)" (vulpea-note-title note) (vulpea-note-id note))))
#+end_src

This function applies to every =vulpea-insert=. Return an empty string
from it to insert a bare id link.

** vulpea-find-backlink

Find notes that link to the current note:

#+begin_example
M-x vulpea-find-backlink
#+end_example

This is useful for discovering connections - seeing what other notes reference the one you're viewing. After you select a note, point lands on the link pointing back to the current note, so you see the mention in its context instead of the beginning of the note.

** Customizing How Notes Are Displayed

By default each candidate shows the note's title followed by its aliases and tags. You can change what every selection command (=vulpea-find=, =vulpea-insert=, and any custom =vulpea-select=) shows by setting two variables:

- =vulpea-select-describe-fn= - builds the main, searchable part of the candidate. It takes a =vulpea-note= and returns a string. The default is =vulpea-note-title=.
- =vulpea-select-annotate-fn= - builds a trailing annotation (shown dimmed). It also takes a =vulpea-note= and returns a string. The default appends the primary title (when matched through an alias) and =#tags=.

For notes that live in headings, two ready-made describe functions prefix the title with its location so same-named notes are easy to tell apart:

#+begin_src emacs-lisp
;; "Projects → Work → Task"
(setq vulpea-select-describe-fn #'vulpea-select-describe-outline)

;; "My Notes → Projects → Task"
(setq vulpea-select-describe-fn #'vulpea-select-describe-outline-full)
#+end_src

Because the whole =vulpea-note= is available, you can assemble any layout you like - directory, outline path, tags, timestamps, even a backlink count - into a single aligned row. See [[file:api-reference.org::*Customizing Selection Display][Customizing Selection Display]] in the API reference for a worked multi-column example, and note that the displayed text does not by itself change the order of candidates - to control the order (say, most recent backlinks first), set a =display-sort-function= through =completion-category-overrides=; see [[file:api-reference.org::*Sorting Candidates][Sorting Candidates]] in the API reference.

Whatever =vulpea-select-describe-fn= builds, the note id is appended to each candidate as an invisible, matchable suffix so ids can be typed to narrow completion (see [[*Selecting by Id][Selecting by Id]]). It is added around your describe function, so it neither shows up in your layout nor needs handling there; =vulpea-select-match-ids= turns it off.

Keep these functions cheap. They run once for every candidate when the finder opens, so heavy work - especially an extra database query per candidate - can make selection slow on large collections. If you need data that is expensive to compute, such as a backlink count, set =vulpea-select-dyncontext-fn=: it runs once per selection, returns a shared value (for example a counts table), and Vulpea hands that value to your describe/annotate functions as a second argument. See [[file:api-reference.org::*Shared context for the whole selection][Shared context for the whole selection]] in the API reference for the full pattern.

Selection also reports a =vulpea-note= completion category, so completion UIs and their extensions (marginalia, embark, consult) can recognize note candidates and annotate or act on them, and each candidate carries its whole note, readable with =vulpea-select-candidate-note=, so code that only sees candidate strings (a sort function, an embark action) can still reach every note field. See [[file:api-reference.org::*Completion Category][Completion Category]].

* Creating Links

** vulpea-insert

Insert a link to another note:

#+begin_example
M-x vulpea-insert
#+end_example

This opens completion to select a note, then inserts an =id:= link at point:

#+begin_src org
See [[id:abc123][Selected Note Title]] for details.
#+end_src

If you type a title that doesn't exist, Vulpea offers to create a new note. See "From vulpea-insert" under Creating Notes for customizing how that note is created.

Typing or pasting the full id of an existing note links that note instead of creating a new one - see [[*Selecting by Id][Selecting by Id]] for details, including how the link description is picked for untitled notes.

* Creating Notes

** From vulpea-find

When you use =vulpea-find= and type a title that doesn't exist, Vulpea asks if you want to create it.

By default the note is created from the typed title via =vulpea-create=. You can customize this - for example to route through =org-capture= for interactive editing - by setting =vulpea-find-default-create-fn= (or passing =:create-fn= to =vulpea-find=). The function is called with the typed title and capture properties (currently always nil) and should return the =vulpea-note= to visit, or nil to skip visiting. This makes "capture on empty" workflows straightforward: a search that finds nothing becomes the start of note creation.

** From vulpea-insert

=vulpea-insert= offers the same when you insert a link to a note that doesn't exist yet. By default the note is created via =vulpea-create= and a link to it is inserted at point.

To customize creation, set =vulpea-insert-default-note-fn= (or pass =:note-fn= to =vulpea-insert=). The contract is the same as for =vulpea-find=: the function is called with the typed title and capture properties (currently always nil) and returns the created =vulpea-note=, or nil to skip. Vulpea then takes care of the rest: it replaces the selected region, inserts the link (using the region text or the note's final title as the description) and runs =vulpea-insert-handle-functions=.

#+begin_src emacs-lisp
(setq vulpea-insert-default-note-fn
      (lambda (title &optional _props)
        (vulpea-create title nil :tags '("inbox"))))
#+end_src

There is also a lower-level =vulpea-insert-default-create-fn= (and =:create-fn=): same arguments, but the function owns the whole flow and must insert the link itself. Use it only when you need to control the link insertion. When both variables are set, the note-fn wins; passing both =:note-fn= and =:create-fn= to =vulpea-insert= is an error.

** Programmatically

For scripts or custom commands:

#+begin_src emacs-lisp
;; Simple creation
(vulpea-create "My New Note")

;; With tags
(vulpea-create "Project Note"
               nil  ; use default file-name template
               :tags '("project" "work"))

;; With metadata
(vulpea-create "Book Review"
               nil
               :meta '(("author" . "Jane Smith")
                       ("rating" . "4")))

;; Without a title: no #+title line is written, the note's title
;; falls back to the file base name (here "scratch")
(vulpea-create nil "scratch.org")
#+end_src

Passing nil as the title works only for file-level notes and needs a
file name that does not depend on the title - see [[*Untitled
Micro-Notes][Untitled Micro-Notes]] for the full story.

** Under Existing Notes

Create heading-level notes inside an existing file using =:parent=:

#+begin_src emacs-lisp
;; Add a heading under an existing note
(let ((parent (vulpea-db-get-by-id "parent-id")))
  (vulpea-create "New Section" nil :parent parent))

;; Control insertion order with :after
(vulpea-create "First" nil :parent parent :after nil)      ; first child
(vulpea-create "Last" nil :parent parent :after 'last)     ; last child (default)
(vulpea-create "After X" nil :parent parent :after "x-id") ; after specific sibling
#+end_src

=vulpea-create-default-template= and =vulpea-create-default-function=
are not consulted for heading-level notes, so pass =:tags=, =:body=,
=:properties=, and =:context= explicitly when you need them.

** Default Templates

Configure defaults that apply to new file-level notes:

#+begin_src emacs-lisp
(setq vulpea-create-default-template
      '(:tags ("inbox")
        :head "#+created: %<[%Y-%m-%d]>"))
#+end_src

Or use a function for dynamic defaults:

#+begin_src emacs-lisp
(setq vulpea-create-default-function
      (lambda (title)
        (list :tags (if (string-match-p "TODO" title)
                        '("task")
                      '("note")))))
#+end_src

→ See [[file:configuration.org][Configuration]] for all template options.

* Working with Metadata

Metadata lets you attach structured data to notes using description lists:

#+begin_src org
#+title: Château Margaux 2015

- country :: France
- region :: [[id:bordeaux-id][Bordeaux]]
- price :: 450
- rating :: 95
#+end_src

** Reading Metadata

In elisp (for scripts or custom commands):

#+begin_src emacs-lisp
(let ((note (vulpea-db-get-by-id "wine-id")))
  ;; Get as string (default)
  (vulpea-note-meta-get note "country")  ; => "France"

  ;; Get as number
  (vulpea-note-meta-get note "price" 'number)  ; => 450

  ;; Get linked note
  (vulpea-note-meta-get note "region" 'note))  ; => <vulpea-note>
#+end_src

For multiple values with the same key:

#+begin_src org
- grape :: Cabernet Sauvignon
- grape :: Merlot
- grape :: Petit Verdot
#+end_src

#+begin_src emacs-lisp
(vulpea-note-meta-get-list note "grape")
;; => ("Cabernet Sauvignon" "Merlot" "Petit Verdot")
#+end_src

** Setting Metadata

In a note buffer:

#+begin_src emacs-lisp
;; Add or update metadata
(vulpea-buffer-meta-set "status" "reviewed")
(vulpea-buffer-meta-set "rating" "95")
#+end_src

To modify a note programmatically and sync immediately:

#+begin_src emacs-lisp
(vulpea-utils-with-note-sync note
  (vulpea-buffer-meta-set "status" "done"))
;; Database is now updated
#+end_src

#+begin_example

** Working with Tags by Note

When you have a note (or note ID) and want to modify its tags without visiting the buffer:

#+begin_src emacs-lisp
;; Get tags for any note
(vulpea-tags note-or-id)

;; Add/remove tags
(vulpea-tags-add note-or-id "new-tag")
(vulpea-tags-remove note-or-id "old-tag")

(vulpea-tags-set note-or-id "only" "these")
#+end_src

To rename a tag across all notes:

#+begin_example

#+end_example

This prompts for the old tag (with completion) and new tag name, then updates all affected notes.

Programmatically:

#+begin_src emacs-lisp
(vulpea-tags-batch-rename "old-name" "new-name")
;; => count of modified notes
#+end_src

** Batch Tag Operations

For operating on multiple notes at once:

#+begin_src emacs-lisp
;; Add a tag to multiple notes
(vulpea-tags-batch-add notes "archived")

;; Remove a tag from multiple notes
(vulpea-tags-batch-remove notes "active")
#+end_src

* Managing Aliases

Aliases are alternative titles for a note, useful when the same concept has multiple names.

** In Your Notes

Aliases are stored in the =ALIASES= property (configurable via =vulpea-buffer-alias-property=):

#+begin_src org
:PROPERTIES:
:ID: abc123
:ALIASES: "PKM" "Personal Knowledge Management"
:END:
#+title: Zettelkasten
#+end_src

Now searching for "PKM" in =vulpea-find= will find this note.

** Adding Aliases

#+begin_example
M-x vulpea-buffer-alias-add
#+end_example

Or programmatically:

#+begin_src emacs-lisp
(vulpea-buffer-alias-add "Alternative Name")
#+end_src

** Removing Aliases

#+begin_example
M-x vulpea-buffer-alias-remove
#+end_example

** Configuring Alias Property

By default, aliases are stored in =ALIASES=. To use =ROAM_ALIASES= for org-roam compatibility:

#+begin_src emacs-lisp
(setq vulpea-buffer-alias-property "ROAM_ALIASES")
#+end_src

* Renaming Notes

When you change a note's title, links pointing to it still show the old title. Vulpea provides tools to propagate title changes across your knowledge base.

** Quick Workflow

1. Edit the =#+title:= line in your note, save
2. If =vulpea-title-change-detection-mode= is enabled, you'll see a notification
3. Run =M-x vulpea-propagate-title-change=
4. Optionally rename the file (y/n)
5. Update link descriptions: [!] all, [r] review, [s] skip, [q] quit
6. Review partial matches manually

** vulpea-propagate-title-change

The main command for updating references after a title change:

#+begin_example
M-x vulpea-propagate-title-change
#+end_example

This command:
- Asks for the old title (if not detected automatically)
- Shows how many links need updating
- Lets you rename the file to match the new title
- Updates link descriptions in other notes

For a preview without making changes, use the prefix argument:

#+begin_example
C-u M-x vulpea-propagate-title-change
#+end_example

** Title Change Detection

Enable automatic detection of title changes:

#+begin_src emacs-lisp
;; For all org files
(add-hook 'org-mode-hook #'vulpea-title-change-detection-mode)
#+end_src

Now when you save a note with a changed title, you'll see:

#+begin_example
Title changed from "Old Name" to "New Name". Run M-x vulpea-propagate-title-change to update references.
#+end_example

** How Links Are Categorized

When you run =vulpea-propagate-title-change=, links are split into:

- *Exact matches*: Link description exactly equals the old title or alias (case-insensitive). These can be auto-updated.
- *Partial matches*: Link description contains the old title but has additional text (e.g., "See Old Title for details"). These are shown for manual review.
- *Custom descriptions*: Link descriptions that don't match are left alone (you chose them deliberately).

** Renaming the File

If you also want to rename the file to match the new title:

#+begin_example
Rename file "old_title.org" → "new_title.org"? (y or n)
#+end_example

The new filename uses the title slug (lowercase with underscores). The database is updated automatically.

You can also rename files programmatically:

#+begin_src emacs-lisp
(vulpea-rename-file note "New Title")
#+end_src

→ See [[file:api-reference.org][API Reference]] for detailed function documentation.

* Moving, Splitting and Merging Notes

Renaming changes a note's file name. These change where a note's content lives. Moving and splitting never rewrite a link, since links are ids and not paths; merging does, because one of the two ids stops existing.

** Moving a Note to Another Directory

Renaming changes the file name and keeps the directory. Moving does the opposite:

#+begin_src emacs-lisp
(vulpea-move-file note "~/vault/projects/")
#+end_src

Or interactively with =M-x vulpea-move-file=, which picks up the note the current buffer visits (point can be anywhere in the file) and completes the target over directories that already hold notes. You are not limited to those: a directory that exists but is still empty can be typed in and confirmed. If you are looking at the note when you move it, the buffer follows the file to its new location.

This is mostly useful when =vulpea-db-sync-directories= has more than one root. New notes are created in the first one (or in =vulpea-default-notes-directory= when set), so moving a note elsewhere afterwards used to mean doing it by hand.

Links keep working, because they are ids and not paths. Nothing is rewritten.

Moving a note outside =vulpea-db-sync-directories= is refused: the note would keep working until the next full scan, then quietly disappear from the database. If you have no sync directories configured there is nothing to check, and any existing directory is accepted.

** Splitting a Heading into Its Own Note

When a heading has grown into its own thing, extract it:

#+begin_src emacs-lisp
(vulpea-split-heading note)
;; or into a specific directory
(vulpea-split-heading note "~/vault/people/")
#+end_src

Interactively, =M-x vulpea-split-heading= works on the heading at point, and the heading does not have to be a note yet: one without an =:ID:= gets one as part of the split, and a file the database has not caught up with is indexed on the spot. Away from a heading (another buffer, or before the first heading of a file) it prompts over the heading notes the database knows. The new file lands next to the source file unless you pick another directory, and it is named after the title slug like any created note.

The heading becomes the file. Its text becomes the =#+title=, its property drawer moves to the file level, and its meta moves with it. Children follow and are promoted, so the shallowest one ends up at level 1. A child that has its own id stays a heading note and keeps that id, it is not split in turn.

The note keeps its id, so every link into it keeps working with nothing rewritten. This is the whole point of doing it through vulpea rather than by hand.

*** Tags a Heading Used to Inherit

A heading's tags include what it inherits from =#+filetags= and from ancestor headings. Once it is a file of its own there is nothing left to inherit from, so those tags are written into the new file:

#+begin_example
#+filetags: :people:          |  #+title: Ada Lovelace
                              |  #+filetags: :people:math:
,* Ada Lovelace :math:        |
#+end_example

Without this the note would quietly drop out of every query filtering on =people=, which is exactly the kind of breakage splitting by hand causes.

This follows =org-use-tag-inheritance=. If you have inheritance off, a heading never had those tags to begin with and only its own travel with it.

The category is carried over the same way, unless it was only the source file's name.

*** What Is Left Behind

By default, nothing. The subtree is removed from the source file. The relationship is still visible through backlinks and unlinked mentions, and for bulk extraction (a contacts file becoming one note per contact) a stub per heading would just be noise.

With a prefix argument the heading is replaced by a link to the new note instead:

#+begin_src emacs-lisp
(vulpea-split-heading note nil t)
#+end_src

#+begin_example
,* Ada Lovelace :math:            ->   * [[id:...][Ada Lovelace]]
  :PROPERTIES:
  :ID: ...
  :END:
  First programmer.
#+end_example

The stub sits at the level the heading had and carries no id of its own, so it stays a pointer rather than becoming a note. It is a real link, so the source file gains a backlink to the extracted note. Tags do not stay behind on it either, they travel with the note, as everything else does.

Reach for this when reading order in the source matters, and for the bulk case leave it off.

The new file is written before the subtree is cut, so a split that fails partway leaves the source untouched rather than losing it.

*** What Cannot Be Split

A heading is refused when it carries a todo keyword, a priority, planning (=SCHEDULED=, =DEADLINE=, =CLOSED=), a logbook, or a =COMMENT= keyword. A file-level note has nowhere to keep any of them, so splitting one would quietly drop the state it was written for. Clock entries are the clearest case: in a file they parse as an ordinary drawer that =org-clock-sum= does not count, so the time would survive as text and stop being time. A =COMMENT= heading is the loudest: it would come back as an ordinary note, exported and visible in the agenda.

All of this is read from the file rather than from the database, so state you added but have not saved yet still counts.

Only the heading's own logbook blocks the split. A child keeps its heading when the subtree moves, so its clocking travels with it and stays valid.

Clear the keyword or the logbook first if the note really should become a file.

The content itself is moved verbatim. If a body happens to contain something that looks like a template placeholder, it stays exactly as written.

** Merging Two Notes

The other direction: note B turns out to belong inside note A.

#+begin_src emacs-lisp
(vulpea-merge source target)
#+end_src

Or =M-x vulpea-merge=, which asks for both.

The source's body is appended to the target under a heading carrying the source's title, and the source's own headings are demoted to sit under it. That is exactly what splitting that heading back out would undo, so the two operations are inverses.

Everything else folds in as well. Tags are unioned, meta is merged key by key keeping both values where they differ, and the source's title and all of its aliases become aliases of the target, so every name it answered to still finds the note.

Links into the source are re-pointed at the target, with descriptions left alone: a link that read the old note's name still reads it. Plain =id:= links count too, not only bracketed ones. Then the source file is deleted.

Both notes have to be file-level. Merging a heading note is a different operation on each side and is refused for now.

A source whose title would not read as itself in a heading is refused as well. =TODO list= becomes a todo heading titled =list=, a title ending in =:word:= is read as tags, and one starting with =COMMENT= hides what follows it. Those change what the note means rather than how it looks, and a merge that did it could not be split back out.

One thing to know: keywords sitting in the source's body, such as a =#+CATEGORY:= or =#+STARTUP:= line below the meta, travel with it and take effect in the target file. Only the source's leading keywords are treated as the note's own.

* Synchronization

** Automatic Sync

With =vulpea-db-autosync-mode= enabled, Vulpea automatically:

- Detects when you save org files
- Detects external changes (git pull, sync tools) if =fswatch= is installed
- Updates the database in the background

You don't need to do anything - it just works.

** Manual Sync

If you need to force a sync:

| Command                            | What it does              |
|------------------------------------+---------------------------|
| =M-x vulpea-db-sync-update-file=   | Update current file       |
| =M-x vulpea-db-sync-full-scan=     | Scan all directories      |
| =C-u M-x vulpea-db-sync-full-scan= | Force re-index everything |

** Checking Sync Status

#+begin_src emacs-lisp
;; Count notes in database
(vulpea-db-count-notes)

;; Check if autosync is running
vulpea-db-autosync-mode
#+end_src

** Encrypted Files

Vulpea can track age-encrypted (=.org.age=) and GPG-encrypted (=.org.gpg=)
org files. See [[file:configuration.org][Configuration → Extra File Extensions]] for setup.

Once configured, encrypted files work like regular org files:
- =vulpea-find= includes them in search results
- Links, tags, and metadata are queryable
- Changes are detected automatically by the sync system

*Note:* Encrypted files are parsed more slowly (via =find-file=) than
regular =.org= files. For large collections, keep the number of
encrypted files manageable.

* Tips and Workflows

** Zettelkasten-Style Notes

1. Create atomic notes with =vulpea-find= (type new title to create)
2. Link related notes with =vulpea-insert=
3. Explore connections with =vulpea-find-backlink=
4. Use tags for broad categories, metadata for specific attributes

- status :: in-progress

#+begin_src emacs-lisp

** Refiling into Your Notes

Vulpea does not need a refile command of its own. =org-refile-targets= accepts a function in its FILES slot, so refile targets can come straight from a vulpea query and stay in sync with your vault:

#+begin_src emacs-lisp
(defun my-vulpea-refile-files ()
  "Return the paths of all file-level notes."
  (seq-map #'vulpea-note-path (vulpea-db-query-by-level 0)))

(defun my-vulpea-refile-verify ()
  "Keep archived subtrees out of refile targets."
  (not (member org-archive-tag (org-get-tags))))

(setq org-refile-targets '((my-vulpea-refile-files :maxlevel . 3))
      org-refile-use-outline-path 'file
      org-outline-path-complete-in-steps nil
      org-refile-target-verify-function #'my-vulpea-refile-verify)
#+end_src

With that in place, =C-c C-w= on any heading offers every note in the vault as a destination, headings up to level 3 included. What each piece buys you:

- =org-refile-use-outline-path 'file= prefixes candidates with the file name and makes the file itself a valid target, so you can refile a heading to the top level of a note, not only under an existing heading.
- =org-outline-path-complete-in-steps nil= hands the whole path to completion at once, which is what interior-matching styles (=vertico=, =orderless= and friends) expect.
- The verify function runs with point on each candidate, and =org-get-tags= includes inherited tags, so children of an archived heading are excluded along with it.

"Every note in the vault" is rarely what you want as you grow past a few hundred notes. Since targets come from a query, narrow the query. For example, refile only into project notes like the ones above:

#+begin_src emacs-lisp
(defun my-vulpea-refile-files ()
  "Return the paths of file-level notes tagged as projects."
  (seq-keep (lambda (note)
              (when (= 0 (vulpea-note-level note))
                (vulpea-note-path note)))
            (vulpea-db-query-by-tags-some '("project"))))
#+end_src

The level check matters: tag queries return heading-level notes too (a heading under =#+filetags: :project:= inherits the tag), so mapping over paths naively yields the same file more than once.

Candidates are collected in the order the function returns them, so sort the query result (say, =seq-sort-by #'vulpea-note-title #'string<=) to put favorite destinations first; whether the completion UI preserves that order depends on its own sorting settings.

Two practical notes. Org visits every target file to collect headings, so on a large vault the first =C-c C-w= takes a moment; setting =org-refile-use-cache= to t caches the targets, and =C-0 C-c C-w= rebuilds the cache when it goes stale. And refile always moves a subtree as a subtree: turning a heading into a file-level note of its own is =vulpea-split-heading=, and folding one note into another is =vulpea-merge= (see [[*Moving, Splitting and Merging Notes][Moving, Splitting and Merging Notes]]).

** Untitled Micro-Notes

Some notes have no meaningful title: quick capture scratchpads, daily
logs, contact cards where the file name is a structured id like
=person-lectia.org=. Vulpea treats these as first class instead of
forcing a sentinel title. Every note records where its title came from
(=vulpea-note-title-source=: =keyword= for =#+title=, =heading= for
heading text, =filename= for the fallback), so "this note is
anonymous" is a fact about the note, not a magic title value.

Create one by passing nil to =vulpea-create=. No =#+title= line is
written; the title you see in queries and completion falls back to the
file base name:

#+begin_src emacs-lisp
(vulpea-create nil "inbox/note.org" :tags '("inbox"))
#+end_src

One wrinkle: without a title, a file-name template referencing
=${title}= or =${slug}= cannot expand (the stock default template
references both), so pass an explicit file name as above or use a
title-free template:

#+begin_src emacs-lisp
(vulpea-create nil nil :tags '("inbox"))  ; with this template it works
;; (setq vulpea-create-default-template '(:file-name "inbox/${timestamp}.org"))
#+end_src

To create micro-notes straight from =vulpea-insert=, plug untitled
creation into =:note-fn= (see [[*From vulpea-insert][From vulpea-insert]]). Here the typed text
becomes the file name, the note itself stays untitled, and the
inserted link picks up the file base name as its description:

#+begin_src emacs-lisp
(setq vulpea-insert-default-note-fn
      (lambda (title &optional _props)
        (vulpea-create nil (format "contacts/%s.org" title))))
#+end_src

By default untitled notes show up in completion under their file-name
title - deliberately named files are a legitimate setup, so nothing is
hidden unless you ask. When the file names are noise (timestamps,
structured ids), hide them opt-in:

#+begin_src emacs-lisp
(setq vulpea-find-default-filter #'vulpea-note-titled-p
      vulpea-insert-default-filter #'vulpea-note-titled-p)
#+end_src

=vulpea-note-titled-p= drops only notes whose title is /known/ to come
from the file name. A note with unknown provenance (say, constructed
by hand in a test or a custom tool) is never hidden. The stricter
=vulpea-note-title-explicit-p= is non-nil only when the title was
written down (keyword or heading) - useful in your own queries.

Hidden notes still need to be reachable: they are one backlink away
from the notes that link to them, and =vulpea-db-get-by-id= always
works. On top of that, ids are matchable in =vulpea-find= and
=vulpea-insert= completion (see [[*Selecting by Id][Selecting by Id]]), so a hidden note is a
typed id away - and since its file-name title is a poor link
description, point =vulpea-insert-default-description-fn= at the id or
your own function so the description is more than the file name.

Adding a title later is just writing the =#+title= keyword: on the
next sync the source flips to =keyword= and the note surfaces in
completion again.

** Grouping Notes by Tag or Content

The [[*Untitled Micro-Notes][micro-notes recipe]] above made single notes untitled. The same
idea scales to a whole group of them: a stream of small notes whose
identity is a shared tag or some shared content, never a title. A
ledger is the classic shape - a pile of entries you keep adding to,
query as a set, and rarely open one by name.

Capture the stream straight from =vulpea-insert= by pointing
=vulpea-insert-default-note-fn= (see [[*From vulpea-insert][From vulpea-insert]]) at an untitled
=vulpea-create= that stamps the shared tag. Each entry lands under a
common directory, carries the =ledger= tag, and writes no =#+title=:

#+begin_src emacs-lisp
(setq vulpea-insert-default-note-fn
      (lambda (title &optional _props)
        (vulpea-create nil
                       (format "ledger/%s.org" title)
                       :tags '("ledger"))))
#+end_src

The typed text is only the file name here; the =ledger= tag is what
ties the entries together. Hide the stream from title completion the
same way the micro-notes recipe does, with =vulpea-note-titled-p= as
=vulpea-find-default-filter= and =vulpea-insert-default-filter=, so it
never clutters the list.

Now work with the whole set at once. The tag is indexed, so pulling
the group is one cheap query:

#+begin_src emacs-lisp
;; every ledger entry, titles never enter into it
(vulpea-db-query-by-tags-some '("ledger"))

;; count them or collect their ids - identity is the id and the tag
(mapcar #'vulpea-note-id
        (vulpea-db-query-by-tags-some '("ledger")))
#+end_src

The grouping key does not have to be a tag. When it lives in the
body - say every entry holds a =#+begin_src ledger= block - group by
content instead. Content is not in the database, so =vulpea-db-query=
runs your predicate over each note in Elisp; here it reads the file
and looks for the block:

#+begin_src emacs-lisp
(vulpea-db-query
 (lambda (note)
   (with-temp-buffer
     (insert-file-contents (vulpea-note-path note))
     (goto-char (point-min))
     (re-search-forward "^[ \t]*#\\+begin_src ledger" nil t))))
#+end_src

This reads every note file, so reach for a tag when you can: the tag
query uses the index and touches no files. Content matching is the
fallback for a group defined by what a note contains rather than by a
label you attached.

Reaching one entry is by id, not by title. The entries are hidden
from completion and their file-name titles are noise, but ids stay
matchable in =vulpea-find= and =vulpea-insert= (see [[*Selecting by Id][Selecting by Id]]), so a
full id typed or pasted narrows to the entry. The file-name title also
makes a poor link description, so use the id there too:

#+begin_src emacs-lisp
(setq vulpea-insert-default-description-fn #'vulpea-note-id)
#+end_src

The title stayed out of the loop the whole way: a tag or the content
defines the group, an id reaches a member, and a query aggregates it.
None of it went through a title.
