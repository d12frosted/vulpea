#+TITLE: Vulpea Design Decisions
#+AUTHOR: Boris Buliga

* Overview

This is a decision log: the choices that shaped Vulpea v2 and why they were made, for contributors who want to know why things are the way they are. It does not describe how the code works today. For that, see [[file:sync-architecture.org][sync-architecture]] (sync and async extraction), [[file:api-reference.org][api-reference]] and [[file:plugin-guide.org][plugin-guide]]. The database schema lives in one place only: =vulpea-db--schema= in the source.

* Where v1 Hurt

Vulpea v1 was a layer over org-roam. It read org-roam's database and extended it through advice, which broke whenever org-roam changed its internals. Any data org-roam did not store meant parsing the file a second time, because org-roam's parse could not be reused.

Indexing happened in save hooks, so every save waited for the database, and changes made outside Emacs (a git pull, Syncthing) went unnoticed until the file was saved again. Reading a note meant assembling it from several tables; v1 bolted on its own materialized table to avoid that, which was one more thing to keep in sync with someone else's schema.

* Decisions

** 1. No org-roam dependency

v2 owns its database and its parser, so the schema, the sync and the extension points can be designed for vulpea instead of worked around. The price was a breaking release, and a compatibility package that would fill org-roam's tables was planned for anyone who needed both.

*Today:* no org-roam dependency. The compatibility package was never written: nobody asked for it, and the two run side by side on separate databases.

** 2. A materialized notes table next to normalized tables

Reading a note is the most common operation, so a note is one row in the =notes= table: no joins to assemble it. This is the materialized view I proposed for org-roam in [[https://github.com/org-roam/org-roam/issues/1997][org-roam#1997]]; an implementation of it for org-roam later measured 25k nodes read in under 0.5 seconds without any cache ([[https://github.com/org-roam/org-roam/issues/2474][org-roam#2474]]).

Filtering needs the opposite shape. Tags, links, metadata and properties also live in normalized tables with indices, so a query filters there and then fetches whole rows from =notes=. The cost is on the write side: every update writes both, and the data is stored twice.

Lists and maps in =notes= (tags, aliases, links, metadata, properties) are JSON. S-expressions would read faster in Elisp, but JSON keeps the database readable outside Emacs, and SQLite can look inside it when it has to.

*Today:* =notes= plus =tags=, =links=, =meta= and =properties=, with =files= for change detection. Programs outside Emacs do read the database directly (see the Ecosystem section of the README).

** 3. File watchers and a queue instead of save hooks

A save hook blocks the save and never sees changes made outside Emacs. File watchers see both, and routing their events through a queue lets many changes land in one transaction. The design came from the sync prototype in [[https://github.com/d12frosted/vulpea/pull/194][vulpea#194]].

*Today:* =vulpea-db-autosync-mode= with filenotify, fswatch, or polling when neither is available. For a long time "non-blocking" only covered scheduling: once a queue timer fired, parsing and writing still ran on the main thread. v2.6 closed that gap with =vulpea-db-async-extraction=, which moves parsing, and optionally the database write, into a background =emacs --batch= worker, and v2.8 turned it on by default. [[file:sync-architecture.org][sync-architecture]] has the details.

** 4. Parse once, feed every extractor

v1 could not reuse org-roam's parse. v2 parses each file once and hands the result to every extractor, and an extractor plugin can declare tables of its own, versioned so its schema can migrate.

*Today:* extractors are registered with =vulpea-db-register-extractor=. The AST is opt-in (=:requires-ast=), because it cannot cross the process boundary to the worker. See [[file:plugin-guide.org][plugin-guide]].

** 5. Headings are notes, and that is configurable

A heading with an =ID= is a note, which is what lets one file hold a whole collection. A collection made only of file-level notes should not pay for walking every heading, so heading-level indexing can be turned off, or limited to some files with a predicate.

*Today:* =vulpea-db-index-heading-level= takes =t= (the default), =nil= or a function of the file path.

** 6. SQLite through EmacsQL

SQLite gives persistence, transactions, foreign-key cascades and indices, and Emacs ships it. Hash tables in Elisp have none of that without rebuilding it by hand, an external database server is too much to ask of an Emacs package, and a custom file format would mean writing a database.

*Today:* EmacsQL on Emacs's built-in SQLite. The hot insert path binds parameters natively (with the same encoding EmacsQL uses), since profiling showed statement compilation dominating bulk writes. The hot read path (loading all notes, tag and link queries) runs SQL through =sqlite-select= and decodes cells the way EmacsQL does, since EmacsQL's per-cell decoding cost as much as SQLite itself when loading every note. Everything else, including plugin queries, goes through EmacsQL.

** 7. org-element for parsing

=org-element-parse-buffer= is what Org itself uses, so extraction sees a file the way Org does. A lighter parser would be faster on common files and wrong on the rest; that option stays open if parsing ever becomes the bottleneck it is not today.

*Today:* files are parsed at element granularity by default (=vulpea-db-parse-granularity=), and unchanged files are not parsed at all (see the next decision).

** 8. Replace a file's rows instead of updating them

When a file changes, its notes are deleted and inserted again rather than updated field by field. There is no need to work out what changed, and a removed tag or link disappears without special handling. This is only affordable because unchanged files are skipped: the =files= table records mtime, size and a SHA256 of the content, and a file is re-read only when they no longer match.

*Today:* =vulpea-db--apply-parse-ctx= does the replace and the sync queue does the check; forced scans skip the check after a settings change.

** Considered, not built: namespaces

Partitioning notes into namespaces (by tags or predicates, each with its own finder) was planned for large collections that mix unrelated kinds of notes. It turned out to be unnecessary: filter functions and the indexed =tags= table cover it, and =vulpea-find= already takes a filter and a candidate source.
